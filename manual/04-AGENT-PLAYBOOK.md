# AI Agent 工程方法论（04-AGENT-PLAYBOOK）

> **定位声明**：用 AI 做开发，日常工作不是简单的"用 AI 写代码"，而是**让 Agent 真正能在业务场景里完成任务**——理解用户意图、调用合适的工具、处理异常结果，并持续验证效果是否稳定的工程。AI 可以加快开发，但**质量责任仍在工程师**。核心交付物是**可观测、可评测、可控制、可兜底、可迭代**的 Agent 系统，而不是一段"像样的回答"。
>
> 本手册既是开发 BugLens 的工作方法，也是 BugLens 产品本身的设计哲学——**我们按本手册的标准建造一个 Agent 系统，并把这套标准产品化**。

## 1. 五性目标（一切设计对着这五条）

| 性 | 定义 | BugLens 落地 |
|---|---|---|
| 可观测 | 每步做了什么、为什么、证据在哪，全程留痕 | Evidence Store 只增；每断言挂证据（02-MANUAL §9） |
| 可评测 | 效果能用数字说话，且可复算 | golden-3 + 基准 + §4 指标体系 |
| 可控制 | 节点/工具/权限有边界，人可随时介入 | 回环 ≤3；PR 只 draft 不合并（S03）；沙箱禁网（T10） |
| 可兜底 | 每个失败路径都有明确降级行为 | 三级模型降级；S05 非标准仓库降级为"定位+建议" |
| 可迭代 | badcase 能回流成改进，而非散落在聊天记录 | badcase 库 + 月蒸馏 + 技能库（02-MANUAL §11/§13） |

**一句话检验**：如果一次运行失败了，你能不能在 10 分钟内指着某条证据说出"错在第几步、为什么"？不能，就先补可观测性，再谈别的。

## 2. 第一步：对齐场景，拆解任务链路

动手前先回答五问（以 BugLens 为例逐条示范）：

1. **今天要解决的业务问题是什么？** 用户只贴一张 UI bug 截图，开发者要自己复现+定位+修复——把这条链路自动化。
2. **Agent 要帮用户完成什么任务？** 输入截图，输出一个"带证据、经过视觉验证、可直接 review"的修复 PR。
3. **什么时候需要调用工具？** 什么时候需要追问用户？**
   - 调工具：需要看真实页面（Playwright）、需要看代码（检索/AST）、需要改代码（补丁）、需要验证（重渲染/测试）——**凡是要"事实"的，一律调工具拿证据，禁止模型凭记忆断言**；
   - 追问用户：截图信息不足（无 bug 位置暗示）、仓库无标准脚手架（S05 触发）、两个根因假设置信度接近且修复方向相反——追问模板预置，一次问清，不挤牙膏。
4. **哪些结果算成功？** 三通道 oracle 通过 + 证据链完整 + 人工 review 可读 = 成功；部分通过 = 降级产出；都不通过 = 明确失败报告（失败也要有交付物：归因证据）。
5. **链路总图**（节点即分工，也是评测的单位）：

```
意图理解(intake) → 复现(reproducer) → 视觉分析(visual_analyst) → 定位(locator)
→ 规划(planner) → 修复(fixer) → 验证(verifier) ⇄(fail≤3 回环) → 审查(critic) → 报告(reporter)
```

**小白提醒**：链路拆不清就画不出验收标准，画不出验收标准就别写代码——这是项目不脱轨的第一道闸。

## 3. 第二步：契约设计（工具/知识库/记忆/权限/验收）

每个节点在开发前先写"契约卡"——九张卡构成系统的静态设计：

| 节点 | 输入 | 输出（state 增量） | 依赖工具 | 权限边界 | 验收标准 |
|---|---|---|---|---|---|
| intake | 截图/文本/issue URL | task_card | 无（纯解析） | 只读输入 | 解析成功率 100%（畸形输入→追问） |
| reproducer | task_card | repro+证据 | Docker、Playwright | 沙箱、禁外网 | 10 次复现产物一致（EXP-03） |
| visual_analyst | 截图 | visual_report+证据 | VLM API | 只读图片 | bbox IoU ≥0.5（EXP-04） |
| locator | visual_report+仓库 | candidates+证据 | AST/BM25/嵌入 | 只读仓库 | top-5 命中（EXP-05） |
| planner | candidates+证据 | hypotheses | LLM | 只读 | 假设可追溯（每条挂证据） |
| fixer | 首选假设 | patch(diff)+证据 | LLM | 只写 worktree 副本 | diff 可 apply、≤3 处改动 |
| verifier | patch | verdict+证据 | 渲染/测试 | 沙箱执行 | 三通道判定、fail 带回环证据 |
| critic | 证据+diff（**不读自述**） | 通过/否决 | 无外部工具 | 只读证据 | 非对称设计（对抗确认偏置） |
| reporter | 全部证据 | PR Markdown | 无 | 只读 | 断言-证据完整性检查 |

三条通用契约原则：
- **知识库**：修复知识住 Repair Wiki（v0.3+）；通用常识住提示词；仓库事实住索引——三者不得混放；
- **长短期记忆**：短期=state（单次运行）；长期=Wiki（跨项目症状→根因）；会话记忆=PROGRESS（开发侧）；
- **权限默认最小**：任何节点想要新权限（如联网）必须显式申请+记录，这是 Agent 安全的底线。

## 4. 第三步：开发——用 AI Coding 提效的正确姿势

| 开发对象 | 做法 | 对应实验 |
|---|---|---|
| 工作流（LangGraph 图） | 先写 state schema 与条件边伪码，让 AI 生成装配代码，人工核对边逻辑 | EXP-07 |
| 工具调用 | 每个工具=纯函数+单测；AI 生成包装，验收以 mock 单测为准 | EXP-03~05 |
| 参数校验 | 一切模型输出过 pydantic；解析失败=异常+原始输出存证据，绝不静默重试 | EXP-04 |
| 重试降级 | 重试 2 次+指数退避→换备选模型→降级模式；降级事件必须可见 | EXP-09 |
| 上下文管理 | 单节点上下文只喂它需要的 state 切片（防上下文膨胀与串扰）；全量证据进 Store 不进提示词 | 全程 |

**提效原则**：AI 写代码、你写契约与验收；AI 生成快，但你 review 的每一行都是你的责任。

## 5. 第四步：Trace 复盘、评测与 badcase 库

- **看 Trace**：每次运行产出"执行轨迹"（节点→输入摘要→输出摘要→证据号→耗时/成本）。调优从通读轨迹开始，不从改提示词开始；
- **评测三件套**：golden-3（开发回归）、基准抽样（每周）、真实仓库演练（M1 起）——三层各答一个问题：代码没坏吗？指标没退步吗？真实世界行吗？
- **badcase 四分类入库**（与 02-MANUAL §13 对齐）：

| 类 | 症状 | 定位法 | 典型修复 |
|---|---|---|---|
| A 选错工具/走错节点 | 轨迹里调了不该调的 | 查节点间传递的 state | 明确触发条件、收紧路由 |
| B 参数填错 | 调对了工具但入参错 | diff 输入与契约 | Schema 校验+few-shot |
| C 幻觉 | 断言无证据支撑 | 证据完整性检查必报警 | 强制证据挂接（硬约束） |
| D 失败兜底缺失 | 出错后行为未定义 | 故意注入故障演练 | 补降级路径 |

- **节奏**：每次实验 15 分钟复盘（02-MANUAL §13）；每周把 badcase 归类统计写进周卡片；每月蒸馏一次进提示词/技能库。

## 6. 第五步：上线前 Review 清单（AI 代码也要人审）

发布（v0.1.0 及以后每次）前逐项打勾：

- [ ] **任务完成**：golden 3/3 绿；指标不退步（对比上一版 REPORT 数字）；
- [ ] **安全边界**：沙箱禁网生效；用户代码只在容器内执行；密钥不出 `.env`/secrets；
- [ ] **权限控制**：无任何节点越权写（fixer 只写 worktree；PR 只 draft）；
- [ ] **异常处理**：断网/限流/超时/畸形输入四类注入演练通过（降级而非崩溃）；
- [ ] **证据完整**：抽 3 份报告做断言-证据对账，零缺失；
- [ ] **成本红线**：单案例 <¥1（S09）；
- [ ] **文档同步**：README/CHANGELOG 与行为一致；表述过 N 红线自查（02-MANUAL §2.3）。

## 7. BugLens 九智能体契约速查（开发时贴在桌上）

见 §3 表格。补充两张"链路状态速记"：
- **成功链**：intake→reproducer→visual_analyst→locator→planner→fixer→verifier(pass)→critic(通过)→reporter→draft PR；
- **降级链**：复现失败→跳转 locator（基于截图+DOM 手工线索）→定位+建议报告；verifier 三连败→归因报告（含失败证据，同样是交付物）。

## 8. 日常节奏：与 AI 协作的一天

```
开工（10 min）  ：读 PROGRESS 末卡片 → 读 01-PLAN 本周行 → 粘贴上下文锚 + 实验指令块
开发（90 min）  ：小步快跑：指令→AI 产出→人工 review→验收命令→commit（每循环 ≤30 分钟）
收工（20 min）  ：实验记录进 REPORT → 每日卡片进 PROGRESS → badcase 归档 → 明日入口写清
每周五（30 min）：对表（八周行项）+ 约束自查 + 目录清洁 + 本周 trace 抽读 3 条
```

**最后重申**：AI 加快的是"从想法到代码"的速度；**系统的可观测性、评测的诚实、控制的边界、兜底的完备、迭代的闭环——这五件事 AI 不会替你负责**。这就是本手册存在的意义，也是 BugLens 这个产品想卖给世界的信念：**Agent 的价值不在"回答得像样"，而在"完成任务可信"。**
